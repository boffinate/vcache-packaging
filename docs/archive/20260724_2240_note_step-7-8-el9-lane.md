# EL9 lane: first coordinated Vinyl 9 + cachetag package cohort

Date: 2026-07-24

Covers plan implementation steps 7 and 8 for the EL9 lane, and the parts of step 9 that a laptop can honestly run: native lint, hardening inspection, and the installed-package smoke. Debian 13 is a separate lane, worked in parallel, in disjoint paths.

Everything below was produced on **aarch64**, in local `almalinux:9` containers on an Apple Silicon host. That is a **process proof, not a release**. The plan is explicit that a developer laptop is not a release build venue; authoritative x86_64 artifacts come from CI. Nothing here is signed, published, or fit to be.

## What now exists

`vcache-packaging/recipes/el9/`:

```text
build.sh                host driver: starts containers, runs nothing itself
cohort.env              pinned inputs; the only place identity values live
container/build.sh      stages: deps, source, vinyl, cachetag, report, lint
vinyl-cache.spec.in     the Vinyl Cache 9 spec, as a substitution template
find-provides           ABI provider generator for the runtime package
systemd/                units, sysusers.d, tmpfiles.d, logrotate, vinylreload
smoke/                  the 11-step installed-package smoke, VCL and backend
README.md
```

One command, `recipes/el9/build.sh`, drives the whole lane: export the pinned source, build the Vinyl SRPM and rebuild it into binary RPMs, install those, build the cachetag SRPM from the canonical tarball and rebuild that, report metadata and digests, inspect hardening, run `rpmlint`, then run the installed-package smoke in a **second, fresh** container that has never seen the build lane.

## Audit: the vendored `pkg-vinyl-cache` RPM material

Read at `upstream/pkg-vinyl-cache/redhat/` (vendored at `27c91305`). It is EL6/EL7-era, and the plan's characterisation of it as source material rather than a base is correct. What it gets right, and what had to change:

**Worth keeping, and kept.** The external dependency-generator mechanism for injecting the VMOD ABI into `Provides` is the right idea and it still works: RPM 4.16.1.3 on EL9 honours `%_use_internal_dependency_generator 0` plus `%__find_provides`, which I verified with a throwaway probe package *before* writing the recipe rather than discovering it after a ten-minute build. It emits `Deprecated external dependency generator is used!` as a warning, which is a note for whoever ports this to EL10 or rpm 4.19+, where the mechanism may finally be gone. The `vmod(<name>)` capability idea for built-in VMODs is also kept.

**Changed, and why:**

| Upstream | Now | Reason |
| --- | --- | --- |
| `%global debug_package %{nil}` | removed | native debuginfo/debugsource generation is a plan requirement, and it works; `export DONT_STRIP=1` in `%install` is kept so there is something to extract |
| `%pre` with `groupadd`/`useradd` | `sysusers.d` + `%sysusers_create_compat` | the EL9-native mechanism; declarative, and the users become package `Provides` (`user(vinyl)`, `group(vinyl)`, …) |
| `%systemd_postun_with_restart` | `%systemd_postun` | restarting an ABI-coupled daemon from a package transaction is precisely the failure mode the packaging plan is trying to design out |
| `%configure --localstatedir=/var/lib` | no override | Vinyl's `configure.ac` derives its state directory as `${localstatedir}/lib/vinyl-cache`, so the upstream override would have produced `/var/lib/lib/vinyl-cache`. This is the sort of thing that survives for years because nothing checks it |
| `Provides`/`Obsoletes` for `vinyl-cache-libs`, `-docs`, `-debuginfo` | dropped | those splits never existed in this project; obsoleting packages that were never published is noise |
| `find-provides` scrapes the version out of `$RPM_BUILD_ROOT` | version-release passed as `$1`, build dir as `$2` | the upstream string surgery worked only because the buildroot path happens to end in `<name>-<version>-<release>.<arch>`. Snapshot versions containing `~` and `.` make that fragile, and a wrong `vmod()` version is invisible until something fails to resolve |
| errors inside `find-provides` could not fail the build | ABI validated in the main shell before reading stdin | the original's provide-emitting subshell ran inside a pipeline, so `set -e` could not save it. A cpp failure degraded silently to a package with no ABI provide at all |
| no ABI sanity check | ABI must be 40 lowercase hex | see the `NOGIT` trap below |
| EL7 `Group:` tags, `%clean`, `BuildRoot` conventions | dropped | obsolete on EL9 |
| `--with-contrib` | dropped | there is no such `AC_ARG_WITH` in this Vinyl's `configure.ac`; it was silently ignored |
| SysV init, `ld.so.conf.d` entry | dropped | systemd-only target, and `libvinylapi` installs into `%{_libdir}` proper, so nothing needs an extra loader path |

**Kept deliberately:** `%global _lto_cflags %{nil}`. LTO is not a hardening flag. Vinyl `dlopen()`s VMODs against symbols exported from the daemon, generates C at run time, and bakes an ABI identity into the result; `-flto=auto -ffat-lto-objects` buys nothing here worth that risk surface.

## The `NOGIT` trap

The plan says to consume an immutable source archive, and the pinned input is a commit, so the export is `git archive`. That drops `.git` — and Vinyl's `include/generate.py` reacts to a missing `.git` by writing the literal string `NOGIT` into `VCS_Version`. **It does not fail.** A build from a naive `git archive` export produces a perfectly well-formed, installable package advertising:

```text
vinyld(abi)(aarch-64) = NOGIT
```

and a cachetag package requiring a real hash would then simply be uninstallable, with nothing in either build log explaining why.

Three defences are now in place, and the redundancy is deliberate because each one catches the failure at a different distance from the mistake:

1. `container/build.sh` synthesises `include/vcs_version.h` and `include/vmod_abi.h` from the pinned commit, exactly as `make dist` from a git checkout would have shipped them;
2. `%prep` refuses to build if either file is absent from the archive;
3. `%build` asserts the built tree's `VMOD_ABI_Version` ends in the pinned commit, before the dependency generator can turn it into a package `Provides`;
4. `find-provides` refuses to emit anything that is not 40 lowercase hex characters.

The archive is otherwise deterministic: `tar --sort=name --mtime=@$SOURCE_DATE_EPOCH --owner=0 --group=0 --numeric-owner --format=gnu`, `gzip -n`.

## Defects found in the cachetag spec scaffolding, and their fixes

This was the scaffolding's first ever build. It came through remarkably well: the build-time assertions ran and passed, `%files` matched reality exactly, `%check` ran, and the ABI dependency landed correctly. Four things needed fixing, all in `libvmod-cachetag/packaging/rpm/libvmod-cachetag.spec`.

1. **Macro expanded in a comment.** The commented-out distro-native variant read `#Requires:      vinyl-cache%{?_isa} = @VINYL_PACKAGE_VERSION@`. RPM expands macros inside comments, so this produced `E: specfile-error warning: Macro expanded in comment on line 64` on every build. Fixed by escaping to `%%{?_isa}`, with a comment saying why, because this is exactly the sort of fix that gets reverted by someone tidying up.
2. **`%description` line too long after substitution.** `Cohort: @COHORT_ID@. Built against Vinyl Cache @VINYL_PACKAGE_VERSION@` is 66 characters as a template and 89 after substitution, tripping `E: description-line-too-long`. This is a general hazard of templated specs — line length has to be budgeted for the substituted value, not the token. Reflowed onto five short lines.
3. **A stale `PREREQUISITE` comment claiming the build would fail.** The `%files` section carried a prominent note that `LICENSE` is absent from `EXTRA_DIST` and that `%license LICENSE` would therefore fail the build until fixed upstream. That was true when the scaffolding was written and is no longer: `LICENSE` is in `Makefile.am`'s `EXTRA_DIST` and is present in `libvmod-cachetag-1.0.0.tar.gz`. Replaced with a note recording that the first real build confirmed it. A comment that predicts a failure which no longer happens teaches the next reader to distrust the comments.
4. **`STATUS: scaffolding, never built`, and the Mock-only build-venue comment.** Both updated: the spec has now been built, and the local proof used `rpmbuild` in a fresh container because Mock needs privileges Docker on macOS cannot sensibly grant. Mock stays a CI requirement.

Also corrected in `packaging/README.md`, restricted to RPM-specific lines because the Debian lane is editing the same file concurrently: the `@VINYL_PACKAGE_VERSION@` row now gives the RPM example alongside the Debian one and says why it is the full `version-release` (that is what an RPM `=` dependency compares against), and the EL9 build-venue bullet records the Mock deferral.

Nothing else in the scaffolding needed changing. `%global __provides_exclude_from`, the `%configure --disable-static --docdir=%{_pkgdocdir}` line, the `.la`/`.a` sweep, the `%check TESTS=cachetag_wal_test` narrowing, and the file list were all correct as written.

One thing the scaffolding is *right* about that surprised me: it does not disable the internal dependency generator, so its `%__provides_exclude_from` filter works. Had it copied the Vinyl spec's external-generator approach, that filter would have silently done nothing.

### A documentation bug found by the smoke test, not fixed here

`purge_header()` returns **`-1` for an accepted purge**; `-2`, `-3` and `-4` are error codes. It is a status, not a count. `USAGE.md`'s example VCL reads:

```vcl
return (synth(200, "Invalidated " + req.http.purged + " objects"));
```

which will tell every user that it invalidated `-1` objects. `USAGE.md` is outside this lane's allowed paths, so it is reported rather than changed. My own smoke VCL initially made the same mistake, which is how it was found.

## Build configuration, as effective

```text
./configure --build=aarch64-redhat-linux-gnu --host=aarch64-redhat-linux-gnu \
  --program-prefix= --disable-dependency-tracking --prefix=/usr --exec-prefix=/usr \
  --bindir=/usr/bin --sbindir=/usr/sbin --sysconfdir=/etc --datadir=/usr/share \
  --includedir=/usr/include --libdir=/usr/lib64 --libexecdir=/usr/libexec \
  --localstatedir=/var --sharedstatedir=/var/lib --mandir=/usr/share/man \
  --infodir=/usr/share/info --disable-static --with-unwind
```

```text
CFLAGS  = -O2 -fexceptions -g -grecord-gcc-switches -pipe -Wall
          -Werror=format-security -Wp,-D_FORTIFY_SOURCE=2 -Wp,-D_GLIBCXX_ASSERTIONS
          -specs=/usr/lib/rpm/redhat/redhat-hardened-cc1 -fstack-protector-strong
          -specs=/usr/lib/rpm/redhat/redhat-annobin-cc1 -fasynchronous-unwind-tables
          -fstack-clash-protection
LDFLAGS = -Wl,-z,relro -Wl,--as-needed -Wl,-z,now
          -specs=/usr/lib/rpm/redhat/redhat-hardened-ld
          -specs=/usr/lib/rpm/redhat/redhat-annobin-cc1
```

These are `%optflags` and `%build_ldflags` verbatim, minus LTO. No `--disable-stack-protector`, no `--enable-developer-warnings`, no `--enable-debugging-symbols`, and no hand-written CFLAGS. That matters more than it looks: as `scripts/test-with-vinyl-cache.sh` documents at length, Vinyl's own `--enable-stack-protector` only appends to `DEVELOPER_CFLAGS`, which reaches `CFLAGS` only under `--enable-developer-warnings`. A build that merely drops the diagnostic flags gets **no** stack protector while `configure` cheerfully reports it as enabled. Under RPM the protection arrives through `%optflags` instead, and the ELF inspection below is what confirms it rather than the configure summary.

`vmoddir`, read from the installed `vinyl-cache-devel` with `pkg-config --define-variable=libdir=/usr/lib64 --variable=vmoddir vinylapi`: **`/usr/lib64/vinyl-cache/vmods`**.

`annocheck` reports `Overall: FAIL (due to MAYB results)` on the runtime objects. Read the reason before acting on it: every `MAYB` is `could not determine how the code was created` / `notes not found and no DWARF info found (could there be a separate debuginfo file?)`. ### EPEL is a runtime dependency too, and that is a decision to revisit

`libunwind.so.8` is in neither EL9 BaseOS nor AppStream, so the **runtime** package needs EPEL, not just the buildroot. This first showed up as the smoke test failing to install `vinyl-cache` in a clean container.

Two things came out of that. First, `--with-unwind` is now **explicit** in `%configure`. Vinyl auto-detects libunwind, so before this change a user-visible runtime dependency was a silent function of what happened to be installed in the buildroot — a package built in a slightly different container would have had a different dependency set with nothing recording the difference. Second, the choice itself is now a recorded trade rather than an accident: unwind is a production panic-backtrace facility and the cachetag harness's production profile keeps it deliberately, so it is kept, and the smoke test enables EPEL with a comment saying it is a genuine prerequisite. **Before this lane is published, decide explicitly whether an EPEL requirement is acceptable for the runtime or whether `--without-unwind` (glibc `backtrace()`) is the better trade.** Installation documentation must state the EPEL requirement either way.

| 3. the `.so` is in the runtime's VMOD directory | `/usr/lib64/vinyl-cache/vmods/libvmod_cachetag.so`, owned by `libvmod-cachetag`, equal to `%{_libdir}/vinyl-cache/vmods` |
| 4. compile VCL with `import cachetag` | `vinyld -C -f` succeeds |
| 5. start Vinyl with Default storage | `Child in state running`; `storage.list` shows `storage.s0 = default` |
| 6. fetch and cache a tagged object | `X-Cache: MISS`, `X-Tag-Objects: 1`, `body: generation=2` |
| 7. warm hit | `X-Cache: HIT`, same `generation=2` |
| 8. purge the tag through the VMOD | `purge_header()` returns `-1`, i.e. accepted |
| 9. old object gone, fresh response served | `X-Cache: MISS`, `body: generation=3` — a different backend generation, so this is a real refetch and not a re-served cache entry |
| 10. stop cleanly | `vinyld` exits on `SIGTERM` |
| 11. uninstall and verify cleanup | every cachetag-owned path removed; the runtime, its VMOD directory and the user's VCL untouched |

Step 9's assertion is worth calling out: the backend increments a generation counter on every hit and puts it in the body, so a warm hit and a post-purge refetch are distinguishable by content. Asserting only on `X-Cache: MISS` would have been satisfied by any cache miss for any reason.

Two of these steps initially failed for reasons in the *test*, not the packages, and both are the kind of mistake that would have silently weakened the gate:

- The readiness probe in step 5 was an HTTP request to the same URL step 6 measures, so step 6's "cold miss" was a warm hit. Readiness is now checked over the `vinyladm` CLI, which does not touch the cache.
- The uninstall check flagged `/usr/lib/.build-id` as left behind. That directory is co-owned by every package shipping an ELF object; the check now skips it.

**SELinux**: `getenforce` is not available in the container and Docker on macOS cannot run enforcing. The `matchpathcon`/`restorecon` context checks and the AVC-denial assertion the plan requires are **deferred to CI**. What was verified locally is the part that does not need SELinux: the VMOD is installed under Vinyl's standard VMOD directory, so a standard-path policy should apply — but that remains a hypothesis until a CI job with enforcing mode confirms it.

## Values for a registry target manifest

Reported, not written: `registry/` and `tools/` are out of scope for this lane, and `cachetag-target/v1` has no fields for the Vinyl packages' own version or source archive anyway. Someone extending the schema needs these.

```yaml
target:
  id: el9-aarch64            # note: NOT the el9-x86_64 the plan's first milestone needs
  distro: el
  distro_release: "9"
  distro_id: el9
  arch: aarch64
  package_format: rpm
  dist_tag: el9
package:
  revision: 1
vinyl_packages:
  runtime_package: vinyl-cache
  dev_package: vinyl-cache-devel
  version: 9.0.0~git20260613.a909548147-1.el9
build:
  profile: production
  image_ref: almalinux:9
  image_digest: sha256:d2515c769e7b73f95c4fde38c0a505336ff38f14990c0b7253b77060a049a743
  compiler: gcc-11.5.0-14.el9.alma.1
  source_date_epoch: "1781652621"
  hardening_check: partial      # readelf pass; annocheck inconclusive without debuginfo
install:
  vmoddir: /usr/lib64/vinyl-cache/vmods
  vmoddir_source: pkg-config
```

Cohort-level inputs, for whenever the first real cohort id is derived: Vinyl version `9.0.0` (snapshot `9.0.0~git20260613.a909548147`), git commit `a90954814766d933a75d4c808c449cb9bc0ae3d3`, VRT `23.0`, strict ABI `a90954814766d933a75d4c808c449cb9bc0ae3d3`, patches `[]`, build profile `production` revision 1, source archive sha256 `bb7e7e38645bd44e4b3e56bf64fe297f8e223ef7a6c267ade4b4cb0a96e8fc69`.

Note that the source archive digest is a **`git archive` export with generated headers injected**, not an upstream release tarball. If the cohort identity is to be a statement about bytes that were compiled — which `registry/README.md` says it is — then the injection step is part of the archive's definition and has to be reproducible. It is (fixed mtime, sorted, `gzip -n`), but it is a step someone else has to be able to repeat, so it belongs in the manifest's provenance rather than being folded silently into a digest.

## Deferred

Everything here is CI work, and none of it is optional before the pre-release the plan describes.

- **x86_64.** This entire lane ran on aarch64. The plan's first milestone is EL9 **x86_64**; nothing here substitutes for it, and the `jemalloc-devel` branch in the spec has never been exercised.
- **Mock clean-room builds.** `rpmbuild` in a fresh container is a good proof that the recipe works, but it is not a minimal buildroot. Mock's value is exposing an undeclared `BuildRequires`, and only Mock provides it. Container `dnf` installs a much wider set than the spec declares, so an undeclared build dependency would not have been caught here.
- **SELinux enforcing.** `matchpathcon`/`restorecon` expectations and the no-AVC-denial assertion.
- **The mismatch fixture and the dnf transaction matrix.** `dnf upgrade`, `dnf upgrade --allowerasing`, `dnf distro-sync`, and direct installation of a mismatched Vinyl package, each from a retained previous cohort or a synthetic fixture, with the resolver outcome published. Step 0c of the smoke proves the *negative install* case only.
- **The full behavioural suite against the production-hardened package build.** Only `cachetag_wal_test` runs at package build time, by design; the VTC suite needs `vinyltest` against a matching running runtime. The plan is explicit that the installed-package smoke does not substitute for it.
- **`annocheck` against installed debuginfo**, so the hardening inspection can be recorded as a pass rather than as partial.
- **The `%check` section of the Vinyl spec.** Vinyl's own `make check` is not run during the package build; the upstream material passes `--define nocheck 1` for the same reason. It is a long, load-sensitive suite and belongs in a CI lane with the `pl00007` flake policy applied, not in every package build.
- **EL10**, which gets its own build, not a rebuild of this one — and which is where the deprecated external dependency generator is most likely to stop working.
- **The `--with-unwind` / EPEL decision**, above.
- **Maintainer identity.** The packages carry `packaging@vinyl-cache.invalid`, from `cohort.env`. That is deliberate: plan implementation step 2, deciding who owns security triage, has not happened, and a real address in a package implies a security contact. No package carrying this address may be published.

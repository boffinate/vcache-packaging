# Cachetag v1.0.1 re-pin: the first buildable public release

Date: 2026-07-28

## The release

Upstream cut cachetag v1.0.1 to fix the defect that made v1.0.0 unbuildable as a package source: the public-release history rewrite had dropped `docs/vmod_cachetag.rst` from `EXTRA_DIST`, while `packaging/README.md` documented it as present in the tarball and both packaging recipes ship it (see the step-1 bring-up note, root cause 2). v1.0.1 restores the file and bumps `AC_INIT` to 1.0.1; the tagged commit `a3897aaccf1d6996c00ee14b2c6e1ddac91ac982` carries committer date 2026-07-28T09:25:37Z (epoch 1785230737).

This is also the repository's first actual GitHub release (flagged prerelease), and its asset URL — `https://github.com/boffinate/libvmod-cachetag/releases/download/v1.0.1/libvmod-cachetag-1.0.1.tar.gz` — is live and serves the pinned bytes, curl-verified against the archive digest.

A correction to the record: the v1.0.0 asset URL was never live. No GitHub release was ever created for v1.0.0 — the tag existed, the release did not, and the URL 404s. The step-10 cohort note's claim that the URL returned 200 was wrong; the nightly-failure investigation had it right (`gh release view v1.0.0` reported no release).

## What was proven before pinning

The archive was built with `scripts/release-source-archive.sh --release` against the digest-pinned upstream `vinyl-cache-9.0.1.tgz` (`2e8ec67c…`). Determinism was shown with `--runs 2` (identical digests `9aba3effcb20cfc70b77a4729990e3cd2ae1712ad242f4e4c45a664e1949eac2`), the from-archive rebuild proof passed 53/53 VTCs, and the metadata sidecar records `worktree_dirty: false` and source-date epoch 1785230737.

One constraint discovered on the way: the script's `--vinyl-git` form cannot build against 9.0.1 because of an upstream VPATH bug — `vmod_math_gen.py` reads `vmod_math_spec.html` without `$(srcdir)/`, fixed upstream after the 9.0.1 tag — so the `--vinyl-tarball` form is required until the release track moves to 9.0.2. This is the third 9.0.1-tarball defect the bring-up has surfaced, after the DESTDIR-less state-directory install and its Debian statedir sibling.

## The pin move

The full pin set moved together, mirroring the v1.0.0 re-pin's footprint: tag `v1.0.1`, peeled commit `a3897aac…`, archive digest `9aba3eff…`, epoch 1785230737, tarball name, and the now-live source URL, across the three workflow env blocks, both lane pin files, and the registry cohort manifest. The package revision restarts at 1 in both lanes (1.0.1-1) because the upstream version moved; 1.0.0-2 was never published and its lanes were proven unbuildable. Both target manifests move to revision 1 and the new epoch, their evidence still pending from the previous reset.

Two additional carriers surfaced by the validator: the template cohort and the distro-native manifest also record `cachetag.version`, which is cross-checked against the sibling checkout's `configure.ac` (now 1.0.1), and selftest's distro-native test validates the checked-in template against a hardcoded expected version. All three moved with the pin. The cohort id `vinyl-9.0.0-4b7e68292979` did not change: its input digest derives from the Vinyl source archive digest, patch series, and build-profile revision — not from cachetag — and `validate` re-derives it cleanly.

## Mock chroot epoch forwarding

The 1.0.0-1 EL9 evidence had already proven that exporting `SOURCE_DATE_EPOCH` on the host does not put it inside mock's chroot: the recorded epoch was the changelog-derived midnight truncation despite the export, and redhat-rpm-config only derives from `%changelog` when the variable is absent from the environment. The fix uses mock's documented mechanism: `container-mock.sh` now generates a small derived config per package — `include()` of the stock `alma+epel-9-x86_64.cfg`, an explicit `config_opts['root']` pin to the stock root name so the shared `--no-clean` root survives, and the package's own epoch in `config_opts['environment']` — and passes it with `-r` for that package's buildsrpm and rebuild. The host export remains as cover outside the chroot; the `use_source_date_epoch_as_buildtime` and `clamp_mtime_to_source_date_epoch` macros remain what turns the value into header bytes. `recipes/el9/container/build.sh` needed no equivalent: plain rpmbuild reads the exported variable directly from its environment.

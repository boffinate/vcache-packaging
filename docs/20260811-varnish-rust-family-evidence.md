# Step 2 evidence: Varnish and varnish-rs (2026-08-11)

This is an evidence ledger, not a build result. “Verified” means read from the pinned catalog, an upstream release/archive, or upstream source metadata. A “prove” item is intentionally left to a fresh target-container build; no host build was run.

## Engine identity, targets, and package evidence

The catalog pins `varnish-9.0.3` to `https://github.com/varnish/varnish/releases/download/varnish-9.0.3/varnish-9.0.3.tar.gz` with SHA-256 `2aac11dd95329b0cea148d478168b3ccc6fe45fab38160c440159386403b69fd`. The upstream release page identifies tag `varnish-9.0.3` and commit prefix `0a62564` ([release](https://github.com/varnish/varnish/releases/tag/varnish-9.0.3)). The archive’s generated `configure` verifies `PACKAGE_NAME=Varnish`, `PACKAGE_VERSION=9.0.3`, `PACKAGE_TARNAME=varnish`, `vmoddir=$(libdir)/@PACKAGE@/vmods`, and `varnishapi.pc.in` (API `libvarnishapi`, `varnishapi.pc`).

Current native target contracts are Debian 13 amd64/arm64, Ubuntu 26.04 amd64/arm64, and AlmaLinux 10 x86_64/aarch64. The Varnish engine row currently selects the four Debian/Ubuntu targets only and has `packages: "false"`; the two EL10 targets are not yet Varnish engine targets. Every target declares a native Docker platform and package architecture in `engines.yml`; later package proof must run on each target added to the Varnish row, including both EL10 architectures before enabling RPM publication.

| Target | Format / declared package architecture | Current Varnish status | Expected package payload to prove |
| --- | --- | --- | --- |
| `debian-13-amd64` | deb / amd64 | engine row selected | runtime daemon/CLI, API shared library and bundled VMODs; `varnish-dev` headers, unversioned API library, `varnishapi.pc`, generators |
| `debian-13-arm64` | deb / arm64 | engine row selected | same manifest, native arm64 objects and dependencies |
| `ubuntu-26.04-amd64` | deb / amd64 | engine row selected | same manifest, native amd64 objects and dependencies |
| `ubuntu-26.04-arm64` | deb / arm64 | engine row selected | same manifest, native arm64 objects and dependencies |

| `el10-aarch64` | rpm / aarch64 | not selected by Varnish row | runtime/devel RPM pair with the same files and exact runtime dependency |

The archive source tree has `include`, `lib`, `bin`, `vmod`, `etc`, `doc`, and `man` install subtrees. Expected runtime payload (the planned family contract) is the daemon and CLI tools, `libvarnishapi.so.*`, bundled VMOD `.so` files under the family VMOD directory, VCL/configuration data, documentation and man pages. Expected development payload is engine headers, unversioned API library, `varnishapi.pc`, autoconf macros, `vmodtool.py`, `vsctool.py`, and VCC/VSC generator data. Exact Debian `.install` and RPM `%files` manifests are **not verified**.

Important archive discrepancy: the same verified 9.0.3 archive contains `bin/vinyld`, `bin/vinyladm`, `lib/libvinyl`, `lib/libvinylapi`, and generated `bin/vinyld/Makefile`; the configure output also defaults `VARNISH_STATE_DIR` to `/var/run` and uses `varnishapi.pc.in` with Vinyl-named source subdirectories. This is incompatible with simply assuming `varnishd`, `varnishadm`, `libvarnish*`, and a `varnish/` VMOD directory. The native arm64 proof below establishes that the installed prefix is Varnish-named on Debian 13; the exact normalized runtime/development manifests still require proof before any Varnish package recipe is published.

Verified configure dependencies for the pinned archive are `pkg-config`, PCRE2 (`libpcre2-8`), libedit (or another readline-compatible library), ncurses/ncursesw, jemalloc when available, and libunwind when `--with-unwind` is selected. The repository’s existing harness additionally needs the normal C/autotools toolchain, Python 3/docutils/Sphinx and a C compiler plus libc development headers because the daemon compiles VCL at load time. Target package names to prove are Debian/Ubuntu `libedit-dev`, `libjemalloc-dev`, `libncurses-dev`, `libpcre2-dev`, `libunwind-dev` and AlmaLinux `libedit-devel`, `jemalloc-devel`, `ncurses-devel`, `pcre2-devel`, `libunwind-devel` (with EPEL/CRB policy as required by the target). Runtime package dependencies must include the exact compiler/libc development capability needed by VCL compilation. Whether any of these are optional in the final Varnish recipe, and the resulting shared-library dependency set on amd64 and arm64, remains a container proof.

## Native arm64 container proof (2026-08-11)

The documented Docker harness built the pinned `varnish-9.0.3` archive on the native `debian-13-arm64` target into `work/step8-varnish-arm64/`. The engine cell passed. Inspecting the resulting prefix in a fresh native Debian container with the prefix runtime libraries installed established the effective identity: `/opt/varnish-9.0.3/sbin/varnishd` reports `varnish-9.0.3` revision `0a625649cd40af4b6c10be5e58a2e89a5e275baa`; `varnishapi.pc` is present; `pkg-config --modversion varnishapi` reports `9.0.3`; and `pkg-config --variable=vmoddir varnishapi` reports `/opt/varnish-9.0.3/lib/varnish/vmods`. The prefix contains the expected bundled `libvmod_*.so` files. The source tree has Vinyl-named internal directories, but the installed prefix is Varnish-named, so the family contract’s daemon, API, and conventional VMOD directory are correct for this target.

Against that prefix, the documented native `reqwest` compatibility cell also passed: it checked out `v0.1.0` at `bd4c8097c035ca1561b062ac3267c88b1057f1b6`, bootstrapped and asserted `rustc 1.90.0` and `cargo 1.90.0` under `/work/rustup` and `/work/cargo`, passed the locked offline metadata preflight, performed the locked fetch phase, built `libvmod_reqwest.so` with `cargo build --release --locked --offline`, installed the declared mapping with the shared artifact validator, and loaded `import reqwest` with the pinned `varnishd`. `cargo-test` remains absent because upstream-suite suitability has not been proved. This was entirely in containers; no host Cargo, Rust, or Autotools build was used.

This proof does **not** enable publication. `varnish-9.0.3` remains `packages: "false"`, so no Varnish engine package, Cargo package/install/load cell, or release payload was attempted. Still required are the Varnish runtime/development package manifests, metadata, fresh-container installation and bundled-VMOD load checks on every enabled Debian/Ubuntu target; native EL10 engine/package proof before adding RPM targets; reqwest package/install/load proof on each candidate target; compatibility/package proof for `fileserver`, `rers`, and `fcgi`; and promotion evidence for every Rust VMOD. The currently promoted Autotools VMODs remain Vinyl-restricted until their own complete Varnish proofs exist.

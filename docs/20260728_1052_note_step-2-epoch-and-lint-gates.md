# Step 2: the EL9 epoch was three lies deep, and both lint gates were decorative

Date: 2026-07-28

## What the scout found on the EL9 epoch

The EL9 lane had no cachetag source-date epoch at all. `recipes/el9/cohort.env` defined only `VINYL_SOURCE_DATE_EPOCH` (1779265093 in the trunk block, 1779093527 in the release block). The cachetag RPM changelog date was substituted from the Vinyl epoch in both build paths (`recipes/el9/container/build.sh` and `scripts/ci/el9/container-mock.sh`), and the cachetag builds inherited the vinyl `export SOURCE_DATE_EPOCH`. So the cachetag package was dated from the Vinyl repository's history.

The recorded manifest value was then neither epoch. EL9's redhat-rpm-config re-derives `SOURCE_DATE_EPOCH` from the topmost `%changelog` entry truncated to midnight UTC, which is the exact arithmetic behind the el9 target manifest's old value: the Vinyl trunk epoch 1779265093 (2026-05-20T08:18:13Z) truncated to 1779235200 (2026-05-20T00:00:00Z). That violated `registry/README.md`'s own schema meaning for `build.source_date_epoch` — a recorded input "from the cachetag release commit".

And the export alone never reached the RPM header bytes anyway: rpm 4.16 ships `%use_source_date_epoch_as_buildtime` defaulting to 0, so `BUILDTIME` came from the wall clock and payload mtimes were unclamped. The mismatch fixture (`recipes/el9/mismatch/container.sh`) has carried `--define "use_source_date_epoch_as_buildtime 1" --define "clamp_mtime_to_source_date_epoch 1"` with a comment explaining exactly this since its reproducibility check first proved the export alone changes nothing; the production paths never adopted it.

What changed: `cohort.env` pins `CACHETAG_SOURCE_DATE_EPOCH=1785138016` (the v1.0.0 release commit's committer date, equal by rule to `recipes/debian-13/pins.env`; the pair must agree and the epoch moves with commit and digest on every re-pin); both build paths derive the cachetag changelog date from it and export it for the cachetag builds; all production build invocations for both packages pass the two epoch macros; and the el9 target manifest records "1785138016" with the old changelog-derived story preserved in its comment. Evidence was already pending from the re-pin, so this was an input correction, not evidence tampering. `_buildhost` remains unpinned deliberately: whole-RPM digest reproducibility is outside the lane's equivalence contract.

## What the scout found on lint

Both lanes' lint stages were decorative. EL9's `stage_lint` ran rpmlint inside `set +e` and discarded the status entirely; there was no rpmlint filter file anywhere, and the only reviewed waiver record was the "Waived, with reasons" Markdown table in the step-7-8 note (`docs/20260724_2240_note_step-7-8-el9-lane.md`), enforced by nothing but the habit of comparing counts (5 errors, 22 warnings at the last recorded run). Debian's `stage-lint.sh` captured lintian's status into `rc`, printed it, and exited 0 — so the step-10 note's claim that "the Debian lane fails on a non-zero lintian exit status" was false.

What changed: the waiver table now lives in-tree as `recipes/el9/rpmlint-waivers.rpmlintrc`, rpmlint 1.11's Python `addFilter` configuration (EL9 AppStream ships 1.11, which predates the TOML config format), every filter carrying its reason in the style of the Debian `.lintian-overrides` files. `stage_lint` runs two passes: an unfiltered informational pass whose full log keeps waived findings visible, then a gating pass with the waiver file whose exit status propagates, plus a "0 errors, 0 warnings" summary assertion that extends the gate to warning-level findings rpmlint's exit status alone would let through. The per-finding filter was chosen over an expected-count tripwire because counts shift for good reasons and a count assertion turns every such shift into unreviewable churn. Debian's stage now exits with lintian's status (free today: the only current finding, `W: wrong-manual-section 3 != 4`, is warning-level) and fails when no `.changes` file was linted at all.

Expected shifts at the cachetag 1.0.1 re-pin: the `invalid-url Source0` warning should disappear now the release URL is live, and the cachetag licence string is now `MPL-2.0 AND BSD-2-Clause`, both halves of which rpmlint 1.11 predates. The gates make those shifts visible instead of silent.

## Validation caveat observed during this work

`python3 tools/release_tool.py validate` briefly failed mid-session with `cachetag.version '1.0.0' does not match configure.ac AC_INIT '1.0.1'`: the sibling `../libvmod-cachetag` working tree advanced to the 1.0.1 preparation commit (`a3897aa`, restoring `docs/vmod_cachetag.rst` to `EXTRA_DIST`) while this repository still pins v1.0.0. Validation against the pinned tag's `configure.ac` (via `CACHETAG_SRC` pointing at a `git show v1.0.0:configure.ac` extraction) passes cleanly, confirming the manifests agree with their pin and the mismatch is working-tree drift ahead of the pending 1.0.1 re-pin, not a defect here. The same drift reaches `selftest` through its three repo-level tests that consult the default sibling checkout (95/98 against the drifted tree, 98/98 with the pinned-tag `CACHETAG_SRC`). Both commands will read clean again from the default path once the 1.0.1 re-pin lands or the sibling checkout returns to the pinned release.

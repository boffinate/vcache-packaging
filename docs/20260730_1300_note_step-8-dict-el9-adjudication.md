# dict EL9 adjudication: pass with a documented exception, and per-scenario outcome pinning

Date: 2026-07-30

Decision owner: repository maintainer. This note records the two decisions that close adjudication items 2 and 3 of [the divergence note](20260730_1139_note_step-8-dict-el9-allowerasing-divergence.md), on the cause established by [the root-cause note](20260730_1231_note_step-8-dict-el9-allowerasing-root-cause.md). It resolves open item 1 of [the Step 8 closing report](20260730_1232_report_step-8-closing.md). The evidence of record is run [30532825959](https://github.com/boffinate/vcache-packaging/actions/runs/30532825959), the deliberate release-transactions dispatch for cohort `vinyl-9.0.1-ac4f719c16f4`.

## Decision 1: dict's EL9 `upgrade_transactions` verdict is `pass`, with the exception documented

`registry/targets/vinyl-9.0.1-ac4f719c16f4/el9-x86_64.yml` now records `pass` for dict, with a field comment naming the three diverging scenarios (`upgrade-allowerasing`, `upgrade-allowerasing-runtime-only`, `distro-sync-allowerasing` — removed with dnf exit 0), the root cause, and this adjudication. With that flip, `validate --require-releasable` accepts the cohort again.

The rationale, in the order it carried weight:

- **The behaviour matches RPM-ecosystem norms.** `--allowerasing` is dnf's explicit erase permission: an operator who passes it has stated that removing installed packages is an acceptable way to complete the transaction. No RPM packager engineers name-order protection against it — the mechanism is not even visible as a mechanism, since nothing about a package name says it is doing resolver work. The ecosystem's sanctioned way to forbid the removal is `/etc/dnf/protected.d/<vmod>.conf`, and that was considered and rejected here: a protected-package file errors out *every* removal, including a deliberate `dnf remove`, which is a semantics change to the package that would need its own documentation and un-protection procedure — a heavier contract than the thing it guards against.
- **The refusal dict fails to reproduce is itself an accident.** cachetag's and redis's exit-1 refusals exist because `libvmod-*` sorts before `vinyl-cache` in libsolv's solvable-ID order; nothing in their packaging asks for the protection, and a rename would silently lose it. Recording dict as `fail` would treat a tie-break artifact as a safety property the other VMODs deliberately provide. They do not.
- **The Debian lane already has these semantics, recorded as `pass`.** `apt full-upgrade -y` removes every VMOD — cachetag included — with exit 0, and the matrix records it as an accepted, warning-required outcome. dict's EL9 erasure is the same operator contract on the other package manager.
- **The divergence dissolves under either future naming standard.** Package-name standardisation (`vmod-*` vs `libvmod-*`) is a live, deliberately undecided question. Standardising on `libvmod-*` makes all three VMODs refuse on dnf 4; standardising on `vmod-*` makes all three erase. Either way the cross-VMOD divergence disappears, so the durable resolution rides the naming decision rather than pre-empting it — which is why **no package rename** is made now, and why fixing dict's name alone (the only rename that would change today's outcome) was rejected as deciding the naming question by side effect.

What changes instead is the operator guidance, which was wrong: Step 9's finding that "bare `--allowerasing` is not the danger on EL9 — only naming a package alongside it is" was measured on cachetag and generalized past its evidence. The [Step 9 report](20260724_2348_report_step-9-transaction-safety.md) and [EL9 lane note](20260724_2342_note_step-9-el9-transactions.md) now carry dated correction sections, and the living [transaction-matrix overview](20260730_0825_note_transaction-matrix-overview.md) states the corrected finding: on EL9 (dnf 4 / libsolv 0.7.24), whether a bare `dnf upgrade --allowerasing` refuses or silently removes a VMOD depends on package-name collation relative to `vinyl-cache` — `vmod-dict` sorts after and is removed with exit 0, `libvmod-*` sort before and are refused with exit 1 — the refusal is not a guarantee, and dict's removal matches the Debian lane's `apt full-upgrade` semantics.

**Untested residual, carried forward:** dnf 5 / newer libsolv (EL10, Fedora) may erase in both name orders — the conditional-best-rule code has moved since 0.7.24, and nothing measured here says anything about it. Whenever an EL10-class target enters scope, its matrix run will answer this against the pins, loudly.

## Decision 2: the EL9 expectation model pins per-scenario outcomes per VMOD

The class-based gate scored both refuse and erase as acceptable outcome classes, so two VMODs diverging on the identical scenario produced no red anywhere — the divergence above was found by a human reading `summary.tsv`, not by the gate. Resolver behaviour keyed on package name is invisible to any gate that does not compare each VMOD's outcomes against a declared expectation. The model is therefore changed: **each VMOD pins the exact expected outcome and package-manager exit code for every scenario, and a measured outcome that differs from its pin fails the matrix.** Cross-VMOD divergence on one scenario is then visible by construction, because the two VMODs carry different pins that were both reviewed.

Implementation, landed with this note:

- **Pins** live in `recipes/el9/transactions/expected/<package>.tsv` and, symmetrically, `recipes/debian-13/transactions/expected/<package>.tsv` — one reviewed, hand-written file per VMOD binary package (`libvmod-cachetag`, `vmod-dict`, `libvmod-redis`), format `scenario TAB expected-exit TAB expected-outcome` in each lane's own summary vocabulary. They sit beside the scenario definitions rather than in the VMOD manifests because the scenario ids and outcome phrases are the lanes' vocabulary (defined by `transactions/scenario.sh` and `container/stage-transactions.sh`), cachetag participates without having an overlay, and both the cachetag and generated-VMOD rows flow through the same two drivers — the manifest would have needed that vocabulary exported across the tool boundary and a second reader per lane. Nothing here is generated, so nothing is hand-patched.
- **The gate** is `tools/ci_matrix.py check-transaction-pins --summary <tsv> --expected <tsv> --format el9|debian [--subset]`, stdlib-only like the rest of `tools/`. Both `recipes/el9/transactions.sh` and `recipes/debian-13/transactions.sh` invoke it after their summary table, keyed on `$VMOD_PACKAGE`, so every transactions-tier row in `vmod-package.yml` gets the check with no workflow edit. It fails on a mismatch (outcome or exit), on a measured scenario with no pin, on a pinned scenario the run did not produce, and on a missing pin file — there is no silent unpinned scenario. `--subset` exists only for local named-scenario runs; CI always runs the full matrix.
- **The pinned values are the measured outcomes of run 30532825959**: dict's three allowerasing scenarios pinned as removed-with-exit-0 (the adjudicated exception), everything else per the recorded `summary.tsv` evidence — for cachetag the Step 9 matrix plus the two same-ABI erasing routes of [the cohort-provide note](20260725_1725_note_step-10-cohort-provide.md), for redis and for the Debian lane the outcome-identical rows the run's registry entries record.
- **The Debian lane is pinned too**, because it dropped out symmetrically: its `SUMMARY.tsv` has the same scenario/exit/outcome shape and stable outcome tokens (`HELD-BACK`, `REMOVED-VMOD`, `REFUSED`, …), so the same checker covers it with a column map. All three VMODs' Debian pins are identical, and a selftest asserts exactly that.
- **Selftests** (`ci_matrix.py selftest`, 319 checks total) cover: pinned-match passes, pinned-mismatch fails (outcome and exit-only), a missing pin fails, a pin without a measured row fails, `--subset`, pin-file rejection cases, and — at repo level — that each checked-in pin file covers its lane's scenario table exactly, that both drivers invoke the gate, that dict's EL9 exception is exactly the three adjudicated scenarios, and that redis's EL9 pins equal cachetag's.

The standing rule the pins create: **a legitimate outcome change must update the pin files, loudly, in review.** The naming standardisation is the expected first case — whichever way it goes, it moves these pins, and the diff is where the maintainer sees the resolver consequence of the name before anything is published. The same holds for a dnf/libsolv behaviour change arriving with a new EL point release: the matrix goes red, and the red is adjudicated rather than absorbed by a class.
